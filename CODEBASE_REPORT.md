# SoundWave Codebase Report

## How to read this report

This is a guided explanation of the entire repository. It is designed to be read in **45–60 minutes**:

1. Read “What the application is” and “How data moves” first (5–8 minutes).
2. Read the root, `types`, `data`, `lib`, and `providers` sections to understand the foundation (12–15 minutes).
3. Read `components` and `app` to understand the visible application (20–25 minutes).
4. Finish with tests, assets, limitations, and suggested next steps (8–12 minutes).

“Block” below means a logical group of code: a type section, helper function, state group, event handler, derived-data calculation, or rendered UI section. Tiny barrel files are explained as one block because every line has the same purpose.

## What the application is

SoundWave is a Phase 1, Spotify-like frontend. It uses:

- Next.js App Router for routes and layouts.
- React client components for forms, local state, context, and the audio player.
- TypeScript for shared data contracts.
- Tailwind CSS for styling.
- Static mock data and browser `localStorage` instead of a backend.
- Node’s built-in test runner for helper and server-rendered component tests.

It supports four account roles:

- **Listener:** browses music, plays tracks, owns playlists, edits a profile, and reads notifications.
- **Artist:** has listener capabilities plus a release-management and revenue dashboard after approval.
- **Support:** handles tickets and artist approval requests.
- **Admin:** controls pricing previews, sees analytics/accounting, and has access to operational routes.

It supports three subscription tiers:

- **Basic:** up to 6 playlists; no avatar editing or offline mode.
- **Silver:** up to 100 playlists; avatar editing and offline mode.
- **Gold:** unlimited playlists; avatar editing, offline mode, and advanced statistics.

The application is functional as a browser mock, but it is not production-secure. Authentication, authorization, uploaded files, pricing changes, ticket changes, and approval changes must eventually move to a backend.

## How data moves

```text
types/                 defines the allowed shapes
   ↓
data/ + constants/     provide initial mock records and settings
   ↓
lib/ + config/         apply rules, formatting, access, and persistence helpers
   ↓
providers/             hold shared browser state (auth, settings, player intent)
   ↓
components/            render reusable controls, cards, layouts, and audio UI
   ↓
app/                   combines everything into routes and user workflows
   ↓
localStorage           persists selected Phase 1 changes in one browser
```

The player has an additional path:

```text
TrackCard / Album page
   → stores a contextual queue
   → updates PlayerProvider
   → PlayerShell resolves the selected Track
   → hidden <audio> performs playback
   → time/end events update the visible controls
```

## `types/`: the shared language

### `types/domain.ts`

This is the canonical domain model.

- **Enum-like union block:** defines roles, gender values, subscription tiers, approval states, ticket states/priorities, notification categories, and the ISO-date alias.
- **`User`:** account identity, login email, role, tier, optional profile details, audit dates, and email-verification state.
- **`ArtistProfile`:** public artist identity, owner link, biography/genres, audience totals, approval state, and optional artwork.
- **`Track`:** playable catalog item with artist/album links, duration, audio/art URLs, streams, explicit flag, release date, and optional lyrics.
- **`Album`:** release metadata and an ordered list of track IDs.
- **`PlaylistItem`:** normalized playlist-membership/audit record for a future backend.
- **`Playlist`:** owner, presentation, visibility, ordered track IDs, and timestamps.
- **`Notification`:** recipient, category, message, read timestamp, and optional destination.
- **`Ticket` / `TicketMessage`:** support workflow header plus public replies or internal notes.
- **`ArtistApprovalRequest`:** submission and review audit trail.
- **`ArtistRevenueRecord`:** stream/revenue/fee/payout values in integer cents.
- **`SubscriptionPrice`:** prices, playlist allowance, and plan entitlements.
- **`AppSettings`:** product-wide editable settings.
- **`PlayerState`:** selected track, queue, playing flag, volume, repeat, and shuffle intent.

### `types/navigation.ts`

- **`NavigationItem`:** visible label, destination, optional description, allowed roles, and an optional future tier gate.
- **`RouteAccessRule`:** protected path prefix and its allowed roles/tier.
- **`SubscriptionFeatureRule`:** complete feature entitlement row for one tier.

### `types/index.ts`

A barrel file. It re-exports both type modules so consumers can write `import type { User } from "@/types"`.

## `lib/`: pure rules and browser persistence

### `lib/auth.ts`

- **`ROLE_HOME_PATH`:** maps every role to its default post-login route.
- **`normalizeEmail`:** trims and lowercases email identity.
- **`findUserByEmail`:** case-insensitive lookup in a supplied user collection.
- **`authenticateUser`:** finds a credential, compares the mock password, then requires a matching user profile.
- **`getPostLoginPath`:** returns the role-specific home path.

### `lib/permissions.ts`

- **`hasRole`:** signed-out users fail; signed-in users pass if their role is listed.
- **`canAccessRoute`:** finds the first configured path prefix. Unlisted paths have no role restriction, but `MainAppLayout` still requires authentication.
- **`filterNavigationForUser`:** removes menu items not allowed for the current role while preserving their full type.

These are UI guards, not a secure backend authorization boundary.

### `lib/subscription.ts`

- Private `getSubscriptionRule` finds a tier’s configuration.
- `getPlaylistLimit`, `hasUnlimitedPlaylistLimit`, and `formatPlaylistLimit` expose limits.
- `canCreatePlaylist` compares current count to the tier limit; infinity needs no special branch.
- `canAccessAdvancedStats`, `canEditProfileImage`, and `canUseOfflineMode` expose individual entitlements.

### `lib/playlist-storage.ts`

- **Key block:** current data is namespaced by user; an older global key is retained for migration.
- **`parsePlaylists`:** safely parses an array or returns `null` for missing/corrupt data.
- **`readStoredPlaylists`:** returns server fallback, current user storage, filtered legacy storage, or seed fallback—in that order.
- **`writeStoredPlaylists`:** serializes one user’s full playlist list.

### `lib/formatters.ts`

Wraps `Intl` for dates, numbers, and currencies. Currency accepts cents and divides by 100. `formatDuration` produces `m:ss`.

### `lib/labels.ts`

Two small accessors return role and subscription display labels from the constant maps.

### `lib/utils.ts`

`cn` removes falsy class fragments and joins the rest, supporting conditional Tailwind classes without another dependency.

## `providers/` and `hooks/`: shared client state

### `providers/AppProviders.tsx`

The root composition order is:

1. `AppSettingsProvider`
2. `AuthProvider`
3. `PlayerProvider`
4. Page content

This gives all routes access to the same settings, account, and player state.

### `providers/AppSettingsProvider.tsx`

- Defines a context containing the current settings and whole-object setter.
- Initializes from `APP_SETTINGS`.
- Memoizes the context value.
- `useAppSettings` returns the context or throws a clear missing-provider error.

Changes are in memory only.

### `providers/PlayerProvider.tsx`

- `DEFAULT_PLAYER_STATE` selects “Neon Rain,” seeds a two-track queue, starts paused, and uses 80% volume.
- Provider state represents shared playback intent.
- It memoizes `{ playerState, setPlayerState }`.
- `usePlayer` enforces the provider boundary.

The actual `HTMLAudioElement` is in `PlayerShell`, not this provider.

### `providers/AuthProvider.tsx`

This is the largest shared-state file:

- **Storage keys:** split current session, users, credentials, and artist applications.
- **Input/result interfaces:** define exactly what each provider action accepts/returns.
- **Context contract:** lists state and account actions exposed to pages.
- **`readStoredValue`:** handles server rendering, missing data, and malformed JSON with a fallback.
- **`writeStoredValue`:** serializes a complete value.
- **`createId`:** creates browser-local IDs.
- **`createUsername`:** slugifies a display name/email and adds a short suffix.
- **State block:** begins from seed users/credentials, no applications, no current user, and “not ready.”
- **Hydration effect:** loads all browser values once, then sets `isAuthReady`. This flag prevents premature redirects.
- **`setCurrentUser`:** synchronizes React session state and local storage.
- **`login` / `logout`:** authenticate and create/remove the stored session.
- **`deleteCurrentUser`:** removes the signed-in user and matching credential, then logs out.
- **`updateCurrentUser`:** merges profile fields, updates last-active time, updates the user list, and refreshes the stored session.
- **`registerListener`:** rejects duplicate email, creates a Basic/unverified listener and credential, persists both, and signs in.
- **`submitArtistApplication`:** rejects an existing account email and stores a pending application without creating a user/session.
- **`requestPasswordReset`:** validates nonempty email and returns mock success; it sends no email.
- **Memoized value and `useAuth`:** publish the state/actions and enforce provider usage.

### `providers/index.ts`

Barrel re-export for all providers and their hooks.

## `components/player/`: actual playback UI

### `PlayerControlsPlaceholder.tsx`

Despite its old name, this is a working controlled component:

- Renders shuffle, previous, play/pause, next, and repeat controls.
- Highlights active shuffle/repeat states.
- Repeat title describes the next cycle action.
- Desktop timeline converts string range values to seconds and reports seeks upward.
- The parent supplies every action, keeping this component independent of the audio element.

### `PlayerTrackSummary.tsx`

Resolves the active track’s artist and album from IDs, renders compact artwork/identity links, and shows stream count for Gold users.

### `PlayerShell.tsx`

This file bridges React state and browser audio:

- **Resolution/state block:** gets global player intent, owns the audio ref, resolves current track/artist, and stores queue/popover/progress/shuffle/repeat UI state.
- **Queue effect:** on track change, resets progress/lyrics and reconstructs a context queue from `soundwave_active_queue`, ignoring bad IDs/JSON.
- **Next handler:** randomly chooses another queue item in shuffle mode; otherwise advances, wraps for repeat-all, or stops at the end.
- **Previous handler:** restarts after three seconds; otherwise goes backward, wraps for repeat-all, or resets.
- **Track-source effect:** reloads audio and resets progress.
- **Play effect:** calls `audio.play()` or `pause()` from context intent; rejected autoplay resets `isPlaying`.
- **Volume effect:** clamps the 0–100 percentage into the audio element’s 0–1 range.
- **Action helpers:** toggle play, change volume, seek, handle end/repeat-one, and cycle repeat mode.
- **Hidden audio block:** emits time/end events.
- **Fixed footer:** summary/mobile mini-controls, desktop full controls, lyric/queue buttons, volume, and popovers.
- **Queue popover:** previews up to five upcoming tracks and allows direct selection.
- **Mobile expanded view:** full artwork, metadata, timeline, controls, and inline scrollable lyrics.

Root Next layout. It defines global metadata, imports global CSS, sets document language, and wraps every route with `AppProviders`.

- Resolves the artist and its tracks/albums.
- Builds the artist-track playback queue.

### `app/playlists/page.tsx` — `/playlists`

- Generates local IDs and resolves artist names.
- Hydrates only the signed-in owner’s seed/stored playlists.
- Central save helper synchronizes component state and local storage.
- Create mode enforces tier limits before opening and again on submit.
- Edit mode prepopulates the shared title modal.
- Create builds an empty private playlist; edit renames one record; delete filters it immediately.
- Each horizontal playlist column has summary/actions and resolves ordered track IDs to TrackCards.
- Add Track links to `/music?addToPlaylist=<id>`.

### `app/artist-dashboard/page.tsx` — `/artist-dashboard`

This is the largest route:

- **Form/view models:** distinguish single/album draft input, managed local tracks, and grouped releases.
- **Media helpers:** derive titles from filenames, recover filenames from URLs, preserve/replace mock URLs, and validate MP3/WAV/FLAC extensions.
- **Creation helpers:** convert single or album form data into `ManagedTrack` records with draft status and mock upload paths.
- **Artist/catalog derivation:** links the current account to its artist, clones catalog tracks with local status, filters owned tracks/albums/revenue, groups album tracks, and computes streams/albums/payout.
- **Approval gate:** only an approved profile can manage catalog entries.
- **Draft handlers:** update fields/type, accept single/multiple files, edit/add/remove album rows, and report validation.
- **Replacement helper:** swaps an edited release’s track group at its old catalog position.
- **Edit flow:** hydrates the form from a release; single saves preserve metrics; album saves require two complete valid tracks and preserve existing metrics by ID.
- **Create flow:** validates artist/approval/title/media; creates one single or a grouped album; stores it locally.
- **Publish/delete:** update every member track of the selected release; delete also cancels an active edit of that release.
- **UI:** identity/permissions, metrics, create/edit form, grouped catalog cards with nested track rows, and monthly revenue table.

No selected file bytes are uploaded. The code only records names under hypothetical `/mock/uploads/...` URLs.

### `app/support/page.tsx` — `/support`

- **Unified approval model:** normalizes seed requests and live signup applications into one queue.
- **Tone maps/helpers:** map status/priority to badges, resolve users, generate local message IDs, and synthesize seed portfolio text.
- **State:** local tickets/messages/filter/reply/note, review overrides, selected approval, and review note.

- **Derived ticket views:** selected ticket, chronological messages, filtered queue, and counts.
- **Ticket actions:** update status; public replies assign staff and set waiting-for-user; internal notes preserve external status; each updates audit time and clears its own input.

- **Ticket workspace:** filterable table plus selected conversation, resolve/close, public reply, and internal note.
- **Approval workspace:** unified table and review modal with portfolio, audit state, note, approve/reject.

## Important limitations and risks

1. **No backend:** refreshes discard many operational changes.
2. **Mock authentication:** passwords are visible plain text and stored client-side.
3. **Client-only access checks:** users can inspect/change browser code and data; APIs must enforce authorization later.
4. **Fake uploads:** file inputs record names but do not upload media.
5. **Partial persistence:** some localStorage changes survive; page-local dashboard/notification changes do not.
6. **No database validation:** most runtime data is trusted after shallow checks.
7. **Player queue split:** global player state and the localStorage context queue are two related sources that a future reducer/service should unify.
8. **Accessibility gaps:** visual modal/tab/player controls need fuller ARIA relationships, labels, focus management, and keyboard behavior for production.
9. **Static analytics:** counts/revenue are computed from small mock arrays in the browser.
10. **Existing lint warnings:** several imports/derived values are unused; they do not fail lint but should be cleaned in a dedicated behavior-aware maintenance change.

## Suggested order for future backend work

1. Replace `AuthProvider` credentials with secure server sessions.
2. Enforce role/tier rules in middleware and every backend endpoint.
3. Replace data modules with typed API clients.
4. Persist playlists, preferences, notifications, tickets, reviews, pricing, and settlements.
5. Implement real media upload/transcoding/storage.
6. Return catalog, stream, and accounting aggregates from the backend.
7. Centralize player queue/actions in a reducer or playback service.
8. Add integration/end-to-end tests for each role and subscription tier.
